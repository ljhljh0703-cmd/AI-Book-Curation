LLM의 역할

LLM은 책 후보를 직접 만들지 않습니다. 후보는 검색과 랭킹이 만들고, LLM은 검증된 후보에 대한 이유만 생성합니다.

점수 추적

qdrantScore, ruleScore, profileVectorScore, lightfmScore, rerankerScore, finalScore를 분리해 어느 단계에서 점수가 바뀌었는지 추적합니다.

비로그인 슬롯과 멀티턴 운영

비로그인 사용자는 계정 기반 개인화가 없기 때문에, 로그인 사용자의 서재/리뷰/온보딩 데이터는 사용하지 않습니다. 대신 제한된 슬롯, 최근 대화 문맥, query 중심 추천, anonymous 후보 압축으로 체험형 추천을 제공합니다.

로그인 멀티턴과 개인화 맞춤

로그인 사용자는 DB에 저장된 세션과 현재 사용자 상태를 사용합니다. 비로그인과 달리 온보딩, 현재 서재, 리뷰/평점, 비선호, 프로필 벡터, LightFM artifact까지 추천에 참여할 수 있습니다.

채팅 세션

로그인 사용자는 서버 DB의 chat session/message를 기준으로 복원합니다. 새로고침 후에도 URL sessionId로 기존 채팅방을 다시 불러옵니다.

AI-server history

AI-server는 최근 대화 일부를 intent classification과 multiturn policy에 사용합니다. 서비스성 질문, 추천 설명 요청, 이전 추천 회피 요청에서 history가 중요해집니다.

멀티턴 액션정책동작
REPLAY이전 추천 다시 보여주기이전 후보를 다시 설명하거나 목록으로 복원
SOFT_DECAY최근 추천 후보에 약한 penalty같은 책이 계속 반복되지 않게 점수를 낮춤. 기본 반감기 30분, 최근 60분 범위
HARD_EXCLUDE명시적 다양성/다른 책 요청최근 추천 후보를 더 강하게 제외. 명시적 회피는 최대 24시간 범위
NONE이전 추천 영향 없음새로운 query/profile 기반으로 추천
개인화 기준: 실시간 추천은 현재 상태를 기준으로 합니다. 학습용 과거 로그와 실시간 추천 이유 근거를 분리해 삭제된 데이터가 다시 설명 근거로 등장하지 않도록 했습니다.

Redis/Valkey 반영 구조

현재 자료는 Redis/Valkey 계층이 반영된 상태를 기준으로 정리했습니다. Redis/Valkey는 source of truth가 아니라 짧게 유지해도 되는 상태, 요청 제한, lock, 캐시에 사용합니다.

비로그인 임시 상태

guest session, guest room, 최근 message/history는 TTL 기반으로 관리하기 적합합니다. 로그인 전환 시 이관하지 않고 폐기해도 됩니다.

Rate Limit / Lock

guestSessionId 또는 IP 기준으로 분당/일일 요청을 제한하고, 같은 메시지 중복 전송을 짧은 lock으로 막습니다.

검색/리랭킹 캐시

동일 query/context of Qdrant 후보, GTE rerank 결과, 추천 응답 일부를 짧은 TTL로 캐시해 반복 요청 비용을 줄입니다.

GTE 리랭킹: query와 profile을 어떻게 넣었나

GTE Query

현재 사용자의 질문을 가장 앞에 두고, 로그인 사용자의 profile summary는 “관련성이 비슷한 후보 간 우선순위 조정”에만 쓰도록 제한합니다.

GTE Document

후보 문서는 title, author, publisher, category, description, table of contents, publisher review만 사용합니다. qdrant/rule/lightfm 점수는 문서 텍스트에 넣지 않습니다.

GTE query 구조 사용자 현재 요청: {query} 우선순위: 현재 요청과 직접 관련된 도서를 가장 우선합니다. 사용자 취향 정보는 관련성이 비슷한 후보 간 우선순위 조정에만 참고합니다. 사용자 취향 요약: {readingPurpose, preferredGenres, likedBooks, readingBooks, readBooks ...} 비로그인 guest=true인 경우: profile summary를 넣지 않고 query 중심으로 rerank합니다.

LightFM: 무엇을 학습시켰나

LightFM은 추천 API 요청 시 학습하지 않고, 미리 만들어진 artifact를 로드해서 Qdrant/rule 후보 50개를 top 20으로 압축하는 역할입니다.

Serving 기준

candidateLimit=50, topN=20, minKnownItems=5. artifact mapping에 user/item이 없으면 추천 API를 중단하지 않고 RULE_BASED로 fail-open합니다.

점수 혼합

LightFM score와 rule score를 0.8 : 0.2로 섞습니다. 모델이 과하게 튀지 않도록 rule score를 보조 안정장치로 둔 구조입니다.

LightFM serving score blended_score = normalized_lightfm_score * 0.8 + normalized_rule_score * 0.2 fallback reasons: LIGHTFM_DISABLED, MISSING_USER_ID, ARTIFACT_LOAD_FAILED, UNKNOWN_USER, NO_KNOWN_ITEMS, INSUFFICIENT_KNOWN_ITEMS, PREDICT_FAILED

페르소나와 실사용자 데이터 구축

왜 persona가 필요했나?

실사용자 행동 데이터는 초기에 sparse했습니다. LightFM은 user-item interaction이 부족하면 UNKNOWN_USER, NO_KNOWN_ITEMS, RULE_BASED fallback이 자주 발생합니다.

왜 Qdrant 실제 도서를 사용했나?

LLM이 가짜 책을 만들지 않도록, persona별 행동은 Qdrant에서 실제 존재하는 도서를 읽어와 생성했습니다.

Nemotron synthetic event 기본 구조 1 persona 기준: - FAVORITE_ADD: 20 - READING_ADD: 3 - READ_ADD: 20 - DISLIKE_ADD: 20 합계 63개 고유 도서 행동. READ_ADD 20권 중 일부에는 rating/review 확장 속성을 붙여 단순 행동이 아니라 취향 강도를 표현했습니다.

source weight

synthetic event에는 source_weight를 적용하고, real event는 학습 시 real_weight_multiplier=2.0으로 더 신뢰하도록 설계했습니다.

user feature

age group, reader type, preferred category, reading purpose hash bucket, profile summary hash bucket, event count bucket을 feature로 내보냅니다.

item feature

도서 feature는 category code, category prefix, publication year bucket, source, language 등 구조화 가능한 값 위주로 구성했습니다.

프롬프트 엔지니어링

1. 후보 밖 생성 금지

LLM은 후보 목록 밖의 책을 추천하지 않습니다. 책 후보는 Qdrant/DB/reranker가 결정합니다.

2. payload 기반 설명

추천 이유는 candidate payload의 title, category, description, evidence에 기반합니다. description에 없는 내용을 지어내지 않도록 제한했습니다.

3. current evidence만 설명

추천 이유에 사용하는 profile evidence는 현재 profile payload에서 온 신호만 사용하도록 제한했습니다.

4. fallback phrase

근거가 약하거나 모델 출력이 불안정하면 특정 장르/도서명 하드코딩이 아니라 일반화된 fallback으로 처리합니다.

프롬프트 핵심 원칙 - 후보 목록 밖의 책을 언급하지 않는다. - candidate payload에 없는 사실은 만들지 않는다. - profile evidence에 없는 사용자 근거를 말하지 않는다. - 추천 이유는 짧고 검증 가능해야 한다. - 모델이 불확실하면 과장하지 않고 fallback한다.

AI-server 중심 문제 해결 사례

통신 오류보다 추천 품질을 바꾼 데이터/랭킹 문제 위주로 정리했습니다.

1
질문이 명확한데도 개인화가 과하게 개입
항상 profile을 강하게 반영하면 사용자가 요청한 주제와 다른 책이 올라오는 문제
기존 문제

“특정 시험/기술/주제 책 추천”처럼 query가 명확한 경우에도 과거 취향이 강하게 섞이면 추천 결과가 어긋날 수 있었습니다.

개선 해결

QUERY_FIRST / HYBRID / PROFILE_FIRST 라우팅을 만들고, QUERY_FIRST에서는 semantic 0.74, profile_vector 0.04처럼 query 관련성을 우선했습니다.

2
비로그인 추천이 로그인 개인화처럼 보이는 문제
guest는 personalized=false로 명확히 분리하고 anonymous score로 후보 압축
기존 문제

비로그인 사용자는 계정 기반 profile이 없는데도 “맞춤 추천”처럼 표현하면 실제 반영 데이터와 설명이 맞지 않습니다.

개선 해결

비로그인은 guest=true, personalized=false로 응답하고, Qdrant 0.45 + rule 0.45 + metadata 0.10의 anonymous selector를 사용합니다.

3
멀티턴에서 같은 책이 반복되는 문제
이전 추천 후보를 무조건 제외하지 않고 요청 성격별로 SOFT/HARD 분리
기존 문제

이전 추천을 전혀 고려하지 않으면 같은 책이 반복되고, 무조건 제외하면 사용자가 “다시 보여줘”라고 했을 때 복원이 어렵습니다.

개선 해결

REPLAY, SOFT_DECAY, HARD_EXCLUDE 정책을 분리했습니다. 일반 추천은 soft penalty, 명시적 다양성 요청은 hard exclude, 다시보기는 replay로 처리합니다.

4
룰베이스가 단순 장르 매칭에 머물던 문제
독서 목적·리뷰·평점·비선호·대상독자까지 점수화
기존 문제

단순 category overlap만으로는 사용자가 왜 그 책을 받아야 하는지 설명하기 어려웠습니다.

개선 해결

purpose, preferred_book, reading_book, read_book, review_positive, audience_bonus와 negative penalty를 분리해 score_detail에 남겼습니다.

5
LightFM이 실제 후보를 점수화하지 못하는 문제
artifact mapping에 user/item이 없으면 fallback
기존 문제

LightFM artifact가 있어도 현재 후보 ISBN이 item mapping에 없으면 모델 점수를 줄 수 없었습니다.

개선 해결

known item만 LightFM score를 계산하고, unknown은 rule backfill로 처리했습니다. known item 수가 5개 미만이면 RULE_BASED fallback합니다.

6
실사용자 데이터 부족으로 학습이 불안정
초기 user-item interaction 희소성 문제
기존 문제

실사용자 데이터만으로는 user-item matrix가 sparse했고, 신규 사용자/신규 후보에서 fallback이 자주 발생했습니다.

개선 해결

Nemotron persona와 Qdrant 실제 도서를 결합해 synthetic event를 만들고, real user event는 multiplier=2.0으로 더 신뢰하게 했습니다.

7
GTE에 숫자 점수를 문서 텍스트로 넣을 위험
reranker 입력 문서는 도서 텍스트만, 숫자 feature는 final fusion에서만 사용
기존 문제

점수 feature를 텍스트에 섞으면 reranker가 자연어 관련성이 아니라 내부 점수 힌트에 끌릴 수 있습니다.

개선 해결

GTE document에는 제목/저자/출판사/분류/소개/목차/출판사 리뷰만 넣고, qdrant/rule/lightfm 점수는 ScoreFusion에서만 반영합니다.

8
Qdrant 검색 지연과 후보 수 조절 문제
검색 100개, rule 50개, personalization 20개, GTE 20개로 funnel 구성
기존 문제

후보 수를 무작정 크게 유지하면 Qdrant 검색, Python 후처리, GTE 호출 비용이 커지고 전체 응답 시간이 늘어납니다.

현재 기준

Qdrant 100 → Rule 50 → Personalization 20 → GTE 20 → Final 5로 단계별 압축하고, Redis/Valkey 캐시로 반복 요청 비용을 줄입니다.

다음 개선

비로그인 추천 고도화

현재는 계정 개인화 없이 anonymous score와 멀티턴 history 중심입니다. 다음 단계는 guest session context를 더 구조화하는 것입니다.

Qdrant 성능 측정

embedding time, qdrant search time, candidate filter time, rerank time, reason generation time을 분리해 p95 개선 전후를 보여줄 수 있습니다.

추천 평가 자동화

후보 준수성, 근거 정합성, 멀티턴 정합성, 개인화 정합성을 평가셋으로 자동 검사하는 방향이 필요합니다.
